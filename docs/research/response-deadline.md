# 原生 Responses 的完整响应超时

冻结源码 `55437a6c98c52bc505de251fca5e80d28b8f860fdafe0c783c8d3de6e6ef2e19` 的公共品案例 `301b63c8-dc2d-41ef-80ac-2c8a4c0df0ce` 配置单次请求超时 60000 ms，却在 220846 ms 后成功返回。原始响应为 completed，没有工具错误，原成功记录不改成失败；但它证明应用未落实所配置的请求时限。

已安装的 OpenAI 客户端在 `fetchWithTimeout` 中等待 fetch 返回后清除计时器。fetch 返回响应头后，响应体仍可能继续等待；应用当时只有 `requestTimeoutMs × maxTurns` 的激活总时限。真实请求没有记录响应头到达时间，不能据此断言远端具体卡在哪一步；本地真实 HTTP 用例已确认完整响应体缺少截止时间。

修复仍使用官方 Agent、Runner、OpenAIProvider、MemorySession 和 tool，通过官方客户端支持的 fetch 选项增加独立 AbortSignal。计时覆盖请求发出、响应头以及完整响应体；透明字节流在 EOF、读取错误或取消时清理计时器，不解析或改写 Responses 事件、工具参数或工具结果。客户端取消信号保持有效，重试仍为零。

到期先标记本次激活失败，再中断底层读取。即使先收到 completed 事件、随后响应体迟迟未结束，整次运行也不能提交。工具回执中的暂存状态、完整流验证与最后的原子提交条件保持不变。配置记录新增 `requestTimeoutScope=headers-and-body`，使新旧时限契约可以区分。

四个故障用例分别模拟仅有响应头、部分工具参数、终止事件后未结束的流，以及未结束的普通 JSON 响应体。修复前均在超过 400 ms 后错误接受成功，修复后均按时失败且没有世界提交。另一个用例验证多次独立请求各自拥有完整预算，前次已完成请求的计时器不会影响后续请求；既有取消、流尾错误、完整原生回执等检查也通过。这些是本地 HTTP 故障注入，不是外部模型行为证据。

单独复测保存案例的入口也有同样的响应体时限缺口。v12 对 `replayDecisionCase` 使用官方请求的 signal 选项，将独立计时器保持到 SDK 完整读取结束；流式、普通 JSON 与旧 SDK 请求都按实际复测时限取消。三个本地 HTTP 用例在修复前均错误接受超过 1000 ms 的成功，修复后均保存超时错误。已收到的 completed 记录仍保留，复测始终不执行返回的世界动作，也不改写原案例；复测配置单独记录 `requestTimeoutScope=headers-and-body`。

原两场对局仍保留为 221 次真实调用、零调用失败、零工具错误、原学习门槛未通过。其协议统计没有原先未纳入的完整响应时限检查，不能拿它替代修复后源码的验证。新批次继续使用原 v5 来源、原两种目标场景和原学习门槛，并独立检查时限作用范围和成功响应耗时。诊断证据见 `data/response-deadline-delivery-1791079755152/deadline-diagnosis.json`。
